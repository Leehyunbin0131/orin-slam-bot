# ROS 2 자율주행을 만들며 배운 것들

> **들어가며**
>
> **시뮬레이션 환경은 결코 현실의 모든 변수를 담아내지 못합니다.** 로봇 주위를 오가는 수십 명의 사람들, 미세한 바퀴의 슬립(Slip), 바닥 마찰력과 조명 변화 등 아무리 가상 환경에서 흉내 내더라도, 결국 현장에 나가는 순간 그 작은 환경 변화 하나로 로봇은 실패를 겪게 됩니다. 저는 시뮬레이션을 절대 과신하지 않습니다. 시뮬레이션은 로봇의 최소한의 기능과 가설을 테스트하는 1차 공간일 뿐이며, 진짜 검증은 언제나 실제 현장에서 다시 이루어져야 합니다.
>
> 여기에 서술된 해결책들 역시 절대적인 정답은 아닙니다. 어느 분야든 문제를 해결하는 방식은 수없이 다양하며, 특히 로보틱스 분야에서는 하드웨어 사양, 소프트웨어 구조, 개발자의 의도 및 로봇의 운용 목표에 따라 저마다 최선의 해법이 달라지기 마련입니다.
>
> 복잡한 현장 속에서 물리적 문제를 정확히 정의하고, 로봇이 주어진 목표를 완수할 수 있도록 최적의 해결책과 합리적인 타협점을 도출해내는 것은 오직 개발자만의 고유한 역할입니다. 이는 AI조차 대신할 수 없는 영역이라 믿습니다.
>
> 저의 경험과 고민의 흔적들이 여러분만의 로봇을 만들어가는 여정에 조금이나마 작은 도움이자 인사이트가 되기를 기대합니다.

---

## 이 문서에 대하여

ROS 2로 자율주행 스택을 구축하면서 **막힌 시간의 대부분은 코드를 잘못 써서가 아니었습니다.** 문법은 맞고 빌드는 통과하며 로그에 에러 하나 찍히지 않는데, 로봇이 원하는 대로 움직이지 않는 상태에서 며칠씩 소모하곤 했습니다.

돌이켜보면 이러한 정체는 특정 프로젝트만의 예외적인 사연이 아니었습니다. **ROS 2 분산 시스템의 구조적 성질에서 비롯되는, 입문자와 개발자가 한 번쯤 반드시 부딪히는 착각과 함정**이었습니다. 따라서 이 문서는 단순한 버그 해결 일지가 아니라, 개발 과정에서 마주치는 대표적인 오해와 실전 대응 원칙을 정리한 가이드입니다.

*본문의 프로젝트 실측 사례와 값들은 저의 로봇과 특정 환경의 기록입니다. 가져가실 것은 개별 수치가 아니라 **"무엇을 기준으로 판단해야 하는가"**입니다.*

## 1. '노드가 켜진 것'과 '정상 동작하는 것'은 다릅니다

런치 파일을 띄웠고 `ros2 node list`에 노드들이 다 보입니다.  
액션 서버 연결도 확인했습니다.

```python
client.wait_for_server() # 서버 접속 확인!
send_goal(goal_pose)     # 하지만 발송한 목표들이 전량 취소(ABORT)되고 갈 수 있는 지점 전체가 영구 블랙리스트로 오염됨!
```

### 왜 이런 일이 생기는가?
일반 프로그램은 실패하면 에러를 던지며 죽지만, **ROS 2의 노드는 죽지 않고 조용히 거절합니다.**
- 라이프사이클 노드가 `unconfigured` 또는 `inactive` 상태이면 모든 요청을 거절합니다.
- 서버 프로세스는 떠 있어도, **전역 코스트맵이 준비되기 전**이면 목표를 받는 즉시 ABORT 처리합니다.

### 해법: 프로세스 존재가 아닌 '눈에 보이는 산출물'로 검증하세요

```python
# 프로세스 접속이 아니라, 실제 결과 데이터(코스트맵/TF) 수신 확인 후 목표 발송
wait_for_topic('/global_costmap/costmap') # 수신 완료!
send_goal(goal_pose)                      # 성공적으로 주행 시작
```

> **완료 판정 규칙**: "노드가 떠 있는가?"가 아니라 **실제 결과 데이터(Topic/TF)가 나오고 있는지**를 확인하십시오.

## 2. 어려운 버그는 대부분 조용합니다

에러 메시지도 없고 로그도 깨끗합니다.  
하지만 로봇이 움직이지 않거나 좌표계가 덜덜 튑니다.

```bash
ros2 node list  # 모든 노드 정상 작동 중인 것처럼 보임
# 데이터가 오지 않거나, TF가 두 노드에서 번갈아 튀어서 주행 불가능!
```

### 왜 통하지 않는가?
ROS 2는 느슨하게 결합된 발행/구독 시스템입니다. **아무도 여러분 대신 연결 오류를 경고해주지 않습니다.**
- **QoS 불일치**: 양쪽 설정이 안 맞으면 데이터가 아예 안 오지만, 에러 로그는 0개입니다.
- **TF 이중 발행**: 두 노드가 같은 좌표계(`odom -> base_footprint`)를 내면 값이 교대로 튀지만, 시스템은 둘 다 정상 발행으로 간주합니다.
- **잔여 프로세스**: 이전 실행의 브리지가 죽지 않고 남아 시계를 이중으로 부르면 TF 버퍼가 계속 지워집니다.

### 반사적으로 확인해야 할 조용한 실패 3대 요소

```bash
ros2 topic info /map -v                  # 1. QoS 호환성 확인 (TRANSIENT_LOCAL vs VOLATILE)
ros2 topic info /clock | grep Publisher # 2. Publisher count가 정확히 1인가?
ros2 run tf2_ros tf2_echo map odom       # 3. TF 타임스탬프가 미래/과거로 튀지 않는가?
```

> 💡 **조용한 오류의 원칙**: 에러 로그가 없다고 정상인 것이 아닙니다. 토픽의 **QoS**, **Publisher 수**, **타임스탬프**를 먼저 의심하세요.

## 3. "성공했다"는 응답을 믿지 마세요

Nav2 액션 서버가 `SUCCEEDED`를 반환했습니다.

```python
result = send_nav_goal(goal) # SUCCEEDED 반환!
# 하지만 로봇은 목표 지점 전방 제자리에 그대로 서 있음! (연속 가짜 성공 발생)
```

### 왜 통하지 않는가?
로보틱스 스택은 허용 오차(`tolerance`)를 두고 동작합니다. 목표 지점이 장애물 팽창 구역에 걸려 있으면, 플래너는 도달 가능한 가장 가까운 지점으로 목표를 당깁니다. **그리고 그 지점이 로봇의 현재 위치면 아무것도 하지 않고 성공을 반환합니다.**

> 💡 **성공 응답의 원칙**: 허용 오차가 있는 시스템에서 "성공"은 *요청한 것*의 완료가 아니라 *타협한 것*의 완료입니다.

### 해법: 상류의 성공 응답을 자기 좌표 기준으로 다시 재검증하세요

```python
result = send_nav_goal(goal)
if result == SUCCEEDED:
    # 로봇의 실제 좌표와 목표 좌표 거리를 직접 계산
    dist = get_distance(robot_pose, goal_pose)
    if dist > tolerance: # 타협된 가짜 성공 감지!
        handle_failure(goal)
```

### ⚠️ 함정: 실패 코드의 종류를 구분하지 않고 일괄 집계하면 안 됩니다

성공만 문제가 아닙니다. **결과 코드는 "목표가 나쁘다"와 "지금이 나쁘다"를 구분해주지 않습니다.**

```python
if result == ABORTED:
    blacklist.add(goal)  # 선점(preemption)까지 단순 실패로 집계하면 정상 지점이 전부 지워짐!
```

- **선점(Preemption)**: 새 목표를 보내면 진행 중이던 목표가 취소되며 실패 코드가 돌아옵니다. **장애가 아니라 정상 동작입니다.**
- **서버 준비 미완료**: 아직 초기화 중이라 거절된 것이지, 그 목표가 나쁜 게 아닙니다.
- **통신 이상**: 위치와 아무 상관없습니다.

앞의 것은 **영구 배제**, 뒤의 것은 **재시도** 대상인데 이 둘을 섞으면 **시스템이 스스로 자기 선택지를 지워 나갑니다.** 자율 동작에서 특히 위험합니다 — 갈 수 있는 곳이 하나씩 "불가능"으로 등록되면서 결국 아무것도 못 하게 됩니다.

> 💡 **실패 분류 규칙**: 실패를 판정하기 전에 **재시도할 실패**와 **영구적으로 포기할 실패**를 반드시 구분하십시오. 또한 주행 진행 여부는 단순 이동 거리가 아닌 **목표 지점까지 남은 거리의 감소량**으로 측정해야 합니다. 복구 동작이 포함된 시스템에서 단순 이동량으로 진행을 측정하면 제자리 왕복조차 정상 주행으로 착각하게 됩니다.

## 4. 파라미터로 풀 수 없는 문제가 있습니다

전역 경로가 벽에 딱 붙어서 나옵니다.  
팽창 파라미터를 대폭 변경해 봅니다.

```yaml
# 팽창 관련 파라미터를 대폭 조정해도 경로가 전혀 변하지 않음!
cost_scaling_factor: <크게 낮춤> / <크게 높임>
```

### 왜 통하지 않는가?
**모든 라이브러리는 특정 상황을 상정하고 설계됩니다.**  
NavFn 플래너의 경우, 코스트맵 변환 계수가 컴파일 시점 상수로 고정되어 있어 설정 파일으로는 벽에서 경로를 떼어놓을 손잡이(Knob) 자체가 존재하지 않았습니다.

### 해법: 파라미터를 크게 바꿔도 반응이 없다면, 즉시 소스코드를 읽으세요

```cpp
// NavFn 소스코드 확인: 변환 계수가 상수로 하드코딩되어 있음을 발견
// 목적 함수를 바깥에서 직접 조정 가능한 SmacPlanner2D로 전환하여 경로 정체 및 주행 시간 대폭 단축!
```

> 💡 **튜닝 규칙**: 파라미터를 대폭 흔들어도 결과가 안 바뀌면, 튜닝을 멈추고 알고리즘의 소스코드를 열어보세요.

## 5. 센서는 자기가 아는 것만 말합니다

라이다 스캔도 정상이고 선반도 보입니다.  
하지만 Nav2가 선반 아래로 경로를 내서 로봇이 상판에 충돌합니다.

```
 [선반 상판]  --> 라이다 평면보다 위에 있어 안 보임!
     |          |
 =====|==========|=====  --> 2D 라이다 스캔 평면
     |          |        --> 기둥 4개만 보이고 사이는 "비어 있음(자유 공간)"으로 적극 보고함!
```

### 왜 통하지 않는가?
2D 라이다는 자기 스캔 평면 밖을 모릅니다. **못 보는 것을 "자유 공간"이라는 적극적인 관측으로 보고**하기 때문에 코스트맵이 셀을 비워버립니다.

### 해법: 센서 화각에 맞는 소거 방식을 분담시키세요

- **2D 라이다 (360도 전방위)**: 광선 추적(Ray Clearing) → 지나온 곳을 다시 보므로 광선으로 지움
- **뎁스 카메라 (좁은 화각)**: 시간 감쇠(Voxel Decay) → 등 돌리면 다시 못 보므로 시간 지나면 지움

> 💡 **센서 수칙**: 센서 스펙보다 **이 센서가 물리적으로 무엇을 못 보고 어떻게 보고하는지**를 먼저 정의하세요.

## 6. 알고리즘의 진짜 입력을 아세요

뎁스 카메라가 벽까지 거리를 mm 단위로 정확히 뱉고 있습니다.  
그런데 로봇이 움직여도 위치 추정이 따라오지 않고 지도가 안 그려집니다.

```
[무늬 없는 흰 벽]  --> 뎁스는 완벽히 정확함 (거리 측정 OK)
                   --> 하지만 RGB 특징점이 0개! 시각 오도메트리 완전 정지!
```

### 왜 통하지 않는가?
"RGB-D 오도메트리"라는 이름 때문에 뎁스가 주역처럼 보이지만, 실제 동작 순서는 이렇습니다.

1. **RGB 영상에서 특징점을 뽑는다** ← 여기가 핵심
2. 다음 프레임에서 같은 특징점을 다시 찾아 **대응**시킨다
3. 뎁스로 각 특징점에 3D 좌표를 붙인다
4. 두 점군을 겹치는 변환을 풀어 이동량을 계산한다

**뎁스의 역할은 3단계(3D 좌표 부여)에 불과합니다.** 실제 로봇의 이동량을 산출하는 핵심 주체는 RGB 특징점이며, 뎁스 센서는 거리 정보를 보조하는 역할을 수행할 뿐입니다. 무늬 없는 벽에서는 1단계에서 이미 실패하므로, 뎁스가 아무리 정확해도 3단계에 전달할 데이터가 존재하지 않습니다.

> 💡 **핵심 입력 원칙**: 이름에서 주역처럼 보이는 입력이 실제 주역이 아닐 수 있습니다. 스펙을 외우기보다 **"어느 입력이 죽으면 전체가 서는가"**를 아는 것이 훨씬 실용적입니다.

### ⚠️ 함정 1: 특징점이 없는 것보다 '틀린 특징점'이 더 위험합니다

특징점을 만들려고 벽에 무늬를 넣을 때, **같은 무늬를 여러 곳에 재사용하면 안 됩니다.**

```
[A구역 벽: 무늬 #5]  ... [B구역 벽: 무늬 #5]  --> 서로 다른 장소를 '같은 곳'으로 오인!
                                              --> 잘못된 루프 클로저 → 지도 전체가 뒤틀림
```

이것을 인지 분야에서 **인지적 모호성(Perceptual Aliasing)** 이라고 부릅니다. 루프 클로저는 "지금 보는 장면과 가장 닮은 과거 장면"을 찾는 일이라, 닮은 장면이 실제로 다른 곳이면 **틀린 두 지점을 하나로 묶어버리고** 그 제약이 지도 전체를 비틀어 놓습니다.

**특징점이 부족하면 위치 추정이 정지할 뿐이지만, 잘못된 특징점이 매칭되면 시스템이 정상으로 착각한 채 잘못된 좌표를 산출합니다.** 후자가 시스템에 훨씬 치명적입니다.

> 💡 **완화책**: 시각으로 후보를 찾고 **기하 구조(라이다 스캔 정합 등)로 교차 검증**하면 시각적으로 닮았어도 기하가 다르면 기각됩니다. 시각과 기하는 서로 독립적으로 틀리므로, 둘을 겹치면 각자의 실패 모드가 상쇄됩니다.

### ⚠️ 함정 2: 해상도를 낮췄더니 정확도가 올라갔습니다

고해상도·고주기로 설정하면 좋아질 것 같지만, 제자리 회전 시 오차가 오히려 폭증하는 경우가 있습니다.

```
[RGB 프레임 t]  +  [뎁스 프레임 t+Δ]  --> 회전 중일 경우 두 프레임의 시점이 서로 달라짐
                                       --> 특징점에 엉뚱한 깊이가 붙음
```

RGB-D 계열은 **한 시점의 RGB와 뎁스가 같은 순간의 장면이라고 가정**합니다. 그런데 렌더링이나 전송이 한 주기 안에 못 끝나면 두 스트림이 서로 다른 시각에 발행되고, 그 틈만큼 특징점에 잘못된 깊이가 붙습니다. **회전이 직진보다 훨씬 나쁜 이유**가 이것입니다 — 짧은 시간에도 시야가 크게 바뀌니까요.

스트림 해상도를 내리어 두 영상이 동일한 주기로 동기화되어 전송되도록 변경하자 위치 오차가 획기적으로 줄어들었습니다. **해상도 감소로 잃은 특징점 수보다 시간 동기화로 얻은 이점이 훨씬 컸기 때문입니다.**

> 💡 **융합 수칙**: **다중 센서에서는 각 센서의 품질보다 센서 사이의 시간 정렬이 먼저입니다.** 좋은 데이터 두 개를 잘못 짝지으면, 나쁜 데이터 두 개를 옳게 짝지은 것보다 못합니다. 성능이 안 나올 때 해상도부터 올리는 것은 대개 반대 방향입니다.

## 7. 정밀도는 측정이 아니라 실행에서 잃습니다

정지 상태에서 마커 인식 정확도가 높은 수준으로 정밀합니다.  
그 값으로 순정 곡선 접근(`opennav_docking`)을 시켰더니 세로 오차가 크게 발생합니다.

```
인식 (정밀) --> [곡선 제어 중 미세 제어 오차 누적] --> 도착 (큰 오차 발생)
```

### 왜 통하지 않는가?
정지 상태의 측정 정밀도와 주행 중 실행 정밀도는 다릅니다. 곡선 접근은 로봇이 움직이면서 제어 오차가 쌓입니다. **정확한 측정값이 있어도 이를 실현할 제어 여유(거리/시간)가 없으면 소용없습니다.**

### 해법: 정지-측정-보정을 단계별(Staging)로 분리하세요

```
[정지] -> [마커 측정] -> [크랩 기동 보정] -> [재정지 & 재측정] -> [후진 접안]
```

- 단계별로 끊어 정지 상태의 인식 정확도를 최종 자세로 그대로 복원.
- 세로 오차를 한 자릿수 mm 단위로 대폭 정밀화!

## 8. 여유는 물리와 추정이 나눠 쓰는 하나의 예산입니다

로봇 폭에 비해 통로 폭에 여유 공간이 있어 보입니다.  
하지만 통로 진입 직후 로봇이 벽을 긁으며 오도메트리가 터집니다.

```
 [통로 벽] |
           |←여유→|  [실제 로봇]
           |        └──── 추정 오차 (여유보다 큼!) ────┘  [로봇이 믿는 위치]
           |
           * 중앙에 있다고 믿으면서 실제로는 벽을 긁고 있음!
```

### 왜 통하지 않는가?
로봇은 스스로 통로 중앙에 위치한다고 추정하지만, **SLAM의 위치 추정 오차**가 통로 측면의 실제 여유 공간보다 크면 추정상 정상 주행 중임에도 섀시가 벽면에 접촉하게 됩니다.

> 💡 **오차 예산 원칙**: **추정 오차 + 주행 흔들림 + 물리적 여유 = 하나의 예산**

### ⚠️ 위험: 주행 실패가 '데이터 파손'으로 번집니다

벽을 긁는 것으로 끝나지 않습니다. 연쇄가 이렇게 이어집니다.

```
벽 긁힘 → 휠 슬립 → 오도메트리 붕괴 → 어긋난 자세로 관측 기록
       → 포즈 그래프에 틀린 제약 삽입 → 지도 전체가 뒤틀림
```

SLAM처럼 **전역 최적화**를 하는 시스템에서는 한 곳의 잘못된 제약이 **멀리 떨어진 구역까지 비틀어 놓습니다.** 즉 "저기서 좀 헤맸다"가 **"결과물 전체를 못 쓰게 됐다"**로 번집니다.

> 💡 **평가 수칙**: **완주율 같은 단일 지표로 자율 시스템을 평가하지 마세요.** 목표는 달성했는데 산출물이 망가진 경우를 통째로 놓칩니다.

### 해법: '진입 가능'이 아니라 '회차 가능(제자리 회전)'을 기준으로 잡으세요

- 차동구동 회차 최소 외접 폭: √2 × 로봇 폭
- 여유 기준을 회차 가능 폭으로 상향 조정.
- 미탐색 구역 탐사 완주 시간을 수십 배 단축!

**들어가는 조건과 나오는 조건은 다르고, 대개 나오는 쪽이 빡빡합니다.** 진입만 검사하면 로봇은 자기가 빠져나올 수 없는 곳에 스스로 들어갑니다.

## 9. 시뮬레이터는 답이 아니라 실험실입니다

시뮬레이션에서 CPU 사용량을 쟀더니 특정 노드가 자원을 크게 소모합니다.  
이 수치로 실기 예산을 세웠더니 과대평가됩니다.

```
Gazebo /clock (1000Hz) -> rclpy 파이썬 콜백 1000번 호출 -> CPU 과도 소모! (실기엔 /clock 없음)
```

### 왜 통하지 않는가?
시뮬레이터가 만들어내는 환경 부하(`/clock` 1000Hz 등)가 측정 대상에 섞입니다. 절대 수치를 그대로 옮기면 측정 대상이 아니라 **측정 환경**을 재게 됩니다.

### 해법: 절대값이 아니라 '같은 환경에서의 A/B 상대 비교'를 이식하세요

| 시뮬레이션으로 검증 가능한 것 | 실기에서 다시 재야 하는 것 |
|---|---|
| 로직/상태 전이가 맞는가 | 자원 사용량의 절대값 (CPU/RSS) |
| 설정 A와 B 중 어느 쪽이 나은가 | 실제 센서 노이즈 및 사각지대 |
| 무엇이 멈추고 무엇이 도는가 | 물리 마찰·슬립 및 최종 정밀도 |

## 10. 원인은 생각해내는 것이 아니라 재는 것입니다

로봇이 좁은 곳에서 멈추자 수많은 가설(CPU 부족, RTF 저하, 팽창 비용 등)을 세우고 시험합니다.  
며칠 동안 하나씩 바꿔봤지만 아무것도 해결되지 않습니다.

### 왜 통하지 않는가?
진짜 원인은 **초기 가설 목록에 아예 없었습니다.** 추측으로 가설을 하나씩 검증하면 시간만 소모됩니다.

### 해법 1: 단순 추측 대신 "소모된 시간이 어디에 쓰였는가"를 정량적으로 측정하세요

```python
# 원인별 소모 시간 배분표(Profiling) 작성
# 특정 서브시스템의 속도 출력 정체 시간이 길다는 것을 관측 -> 내부 소스 직행 후 해결!
```

> 💡 **프로파일링 수칙**: 단순 추측에 의존하지 말고 소모 시간과 자원의 배분표(Profiling)를 작성하십시오. 배분표는 올바른 가설을 도출해주지만, 가설만으로는 객관적인 배분 현황을 파악할 수 없습니다.

### 해법 2: 눈에 안 보이는 산출물은 '그림'으로 뽑아 비교하세요

로보틱스의 중간 산출물은 대부분 **원래 눈으로 볼 수 있는 형태**입니다 — 지도, 코스트맵, 경로, 검출 결과, 점군. 그런데 이걸 로그 한 줄로 압축해 놓으면 **"값이 조금씩 줄어들고 있다"** 같은 변화가 전혀 보이지 않습니다.

```
[로그만 볼 때]   "탐사가 이미 간 곳을 자꾸 다시 감" --> 원인 추정 불가
[이미지로 뽑을 때] 지도가 자라다가 '줄어드는' 프레임 발견 --> 즉시 원인 특정!
```

> 💡 **시각화 수칙**: RViz 및 이미지 렌더링을 적극 활용하여 중간 산출물을 시각적으로 비교하십시오. 텍스트 로그상으로는 수주간 파악하기 힘들었던 오류가 시각화 프레임 비교를 통해 단번에 규명되는 경우가 많습니다.

### 해법 3: 한 번에 하나만 바꾸고, '아니었던 것'도 기록하세요

두 개를 같이 바꾸면 **순효과만 보입니다.** 좋아졌다면 나쁜 쪽 변경까지 그대로 안고 가게 됩니다.

그리고 **직관과 반대로 나오는 경우가 많습니다.** "감지를 더 빨리 하면 낫겠지" 싶어 반응 시간을 줄였는데, 앞의 조치가 자리 잡기 전에 다음 조치가 들어와 서로를 방해하며 오히려 나빠지는 식입니다. **그래서 재야 합니다.**

> 💡 **기록 수칙**: 검증을 통해 기각된 가설을 반드시 문서로 기록해 두십시오. 기각 기록이 없으면 추후 동일한 무의미한 테스트를 반복하게 됩니다. 실패한 가설 목록은 성공 기록만큼이나 가치 있는 자산입니다.

## 11. 시작하는 분께 — 순서와 습관

### CLI 디버깅 습관 (ROS 2의 디버거)

```bash
ros2 topic info <토픽> -v        # QoS 호환성 확인 (조용한 실패 1순위 원인)
ros2 topic info /clock          # Publisher count가 1인가?
ros2 run tf2_ros tf2_echo A B    # 좌표계가 실제로 조회되는가
ros2 lifecycle get <노드>       # 상태가 active인가
```

### 추천 공부 순서

1. **TF를 제대로 이해하기**: 초보자 고통의 상당 부분이 TF입니다. 좌표계 규약(`map -> odom -> base_footprint`)을 대충 넘기지 마세요. 여기서 아낀 하루가 나중에 일주일을 벌어줍니다.
2. **통신 3종과 QoS**: 토픽·서비스·액션의 쓰임새 차이와 QoS가 왜 연결을 끊는지 이해하세요.
3. **런치와 파라미터 구조**: 시스템이 조금만 커지면 여기서 무너집니다.
4. **그다음에 대형 스택**: Nav2, VSLAM 같은 거대 모듈로 넘어가세요.

### 로봇의 실제 숫자를 머리에 넣으세요

CAD 도면 수치에 의존하지 말고 실제 기기의 물리적 수치를 직접 측정하십시오. 실제 추정 오차와 물리적 사각지대를 파악해야만 정상 운용 가능 여부를 정확히 판단할 수 있습니다.

- 로봇의 실제 치수와 제자리 회전에 필요한 공간 (**√2 × 폭**)
- 센서가 **어디에 어떤 각도로** 달렸고, 어디를 못 보는지
- 내 위치 추정이 **몇 cm 오차**를 갖는지

### 상시 기동 점검 5대 수칙
- [ ] 핵심 토픽이 **실제 데이터로** 나오는가 (`ros2 topic hz`)
- [ ] 시계/TF 토픽의 **발행자 수가 1인가**
- [ ] 라이프사이클 노드가 **`active` 상태인가**
- [ ] TF 트리가 **단절 없이 연결되어 있는가**
- [ ] 이전 실행의 **잔여 프로세스가 정리되었는가**

## 마치며

ROS 2 개발 과정에서 가장 자주 마주치는 순간은 **로그는 멀쩡한데 로봇이 움직이지 않는 상황**입니다.

이 순간은 실패가 아니라, **어떤 데이터를 계측하여 현상의 원인을 밝혀낼 것인가**라는 질문으로 넘어가 엔지니어로서 가장 크게 성장하는 지점입니다.

로봇은 물리적 세상에서 동작하기에 항상 수많은 변수에 노출되어 있습니다. 단순한 성공/실패라는 단일 결과에 일희일비하기보다, **문제를 정확히 정의하고 데이터에 기반하여 원인을 잘라내는 과정 자체**를 즐기시기를 응원합니다.
