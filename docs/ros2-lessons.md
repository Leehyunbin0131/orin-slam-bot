# ROS 2 자율주행 스택 구축의 본질과 엔지니어링 인사이트

> **서문**
>
> **가상 시뮬레이션 환경은 현실 세계의 수많은 동적 변수를 결코 완벽히 재현할 수 없습니다.** 로봇 주위를 불규칙하게 오가는 보행자들, 바퀴의 미세한 슬립(Slip), 바닥 면의 마찰력 균일도, 광원 변화 등 가상 공간에서 아무리 정밀하게 모사하더라도, 실제 현장에 투입되는 순간 아주 작은 환경적 변수 하나로 인해 로봇은 예상치 못한 실패에 직면하게 됩니다. 따라서 시뮬레이션을 과신해서는 안 됩니다. 시뮬레이션은 최소한의 알고리즘 가설과 로직을 검증하는 1차 시험대일 뿐이며, 최종적인 완성도 검증은 언제나 실제 물리 현장에서 이루어져야 합니다.
>
> 본 문서에 제시된 해결책들 역시 단 하나의 절대적인 정답이 아닙니다. 로보틱스 분야에서는 하드웨어 사양, 소프트웨어 아키텍처, 운용 목적 및 설계자의 의도에 따라 최선의 해법과 타협점이 완전히 달라집니다.
>
> 복잡한 현장 속에서 물리적 본질을 정확히 정의하고, 로봇이 주어진 미션을 완수할 수 있도록 최적의 아키텍처와 합리적인 마진을 도출해 내는 것은 오직 엔지니어만의 고유한 영역입니다. 이는 인공지능조차 대신할 수 없는 고도의 판단 과정입니다.
>
> 본 기록에 담긴 치열한 고민과 시행착오의 흔적들이 여러분만의 독창적인 로봇을 구축해 가는 여정에 깊이 있는 통찰과 이정표가 되기를 바랍니다.

## 본 문서의 목적

ROS 2 기반 자율주행 스택을 구축하는 과정에서 **가장 많은 시간을 소모하는 순간은 코드 문법 오류나 빌드 실패 때문이 아닙니다.** 문법은 타당하고 컴파일은 정상 완료되며 런타임 로그에 단 하나의 에러도 찍히지 않는 상태에서, 로봇이 원하는 대로 동작하지 않아 원인을 추적하느라 며칠씩 정체되곤 합니다.

돌이켜보면 이러한 정체 현상은 특정 프로젝트만의 이례적인 사건이 아니었습니다. **ROS 2 분산 아키텍처 특유의 성질에서 비롯되는, 수많은 개발자가 한 번쯤 반드시 부딪히는 구조적 착각과 함정**이었습니다. 따라서 본 문서는 단순한 버그 수정 일지가 아닌, 자율주행 개발 과정에서 마주치는 대표적인 오해와 실전 대응 원칙을 체계적으로 정리한 엔지니어링 가이드입니다.

*본문에 기술된 실측 수치와 사례는 특정 하드웨어 및 테스트 환경의 결과물입니다. 본 문서에서 취해야 할 핵심은 개별 데이터 수치가 아닌 **"어떤 관점과 기준으로 현상을 해석해야 하는가"**에 대한 분석 프레임워크입니다.*

## 1. '노드의 가동'과 '정상 서빙'의 격차

런치 파이프라인을 실행했고 `ros2 node list` 상에 모든 노드가 정상 등록되어 있습니다. 액션 서버 바인딩 역시 통과한 상태입니다.

```python
client.wait_for_server() # 서버 바인딩 확인 완료
send_goal(goal_pose)     # 전송한 이동 목표가 전량 취소(ABORT)되며, 도달 가능한 후보 지점 전체가 차단 리스트로 오염되는 현상 발생
```

### 메커니즘 분석
일반 단일 애플리케이션은 예외 상황 발생 시 엑시트 코드와 함께 종료되지만, **ROS 2 아키텍처의 노드는 예외를 던지며 종료되는 대신 프로세스를 유지한 채 정중히 요청을 거절합니다.**
- Lifecycle 노드가 `unconfigured` 또는 `inactive` 상태일 경우 외부 요청을 수신하더라도 이행하지 않고 거부합니다.
- 서버 프로세스가 상주하고 있더라도, **전역 코스트맵(Global Costmap)의 초기화가 완료되기 전**이라면 전송된 Goal을 즉시 ABORT 처리합니다.

### 원칙: 프로세스 상주 여부가 아닌 '실제 산출 데이터'로 서빙 상태를 검증하십시오

```python
# 단순 프로세스 연결이 아닌, 바인딩된 토픽/TF 데이터 수신을 확인한 후 명령 전달
wait_for_topic('/global_costmap/costmap') # 데이터 파이프라인 수신 확인 완료
send_goal(goal_pose)                      # 정상적인 자율주행 기동
```

> **검증 원칙**: "노드가 프로세스 목록에 상주하는가?"가 아닌, **후속 파이프라인이 소비할 실제 결과 데이터(Topic/TF)가 수신되고 있는가**를 기준으로 판단해야 합니다.

## 2. 치명적인 오작동은 대부분 정적 속에 찾아옵니다

런타임 에러 메시지나 경고 로그는 일절 출력되지 않습니다. 그러나 로봇은 제자리에 고정되어 주행하지 못하거나 좌표계 프레임이 불규칙하게 진동합니다.

```bash
ros2 node list  # 모든 노드가 정상 작동 중인 것으로 표시됨
# 데이터 스트림이 유실되거나, TF 타임스탬프가 서로 다른 노드에서 번갈아 발행되어 좌표 붕괴 발생
```

### 메커니즘 분석
ROS 2는 느슨하게 결합된 발행/구독(Publish/Subscribe) 패러다임을 취합니다. **시스템은 연결 매칭에 실패하더라도 개발자에게 경고를 보내지 않습니다.**
- **QoS 프로필 불일치**: 퍼블리셔와 서브스크라이버 간 QoS 트랜잭션이 상호 호환되지 않으면 데이터 통신이 차단되지만, 에러 로그는 전혀 기록되지 않습니다.
- **TF 이중 발행 (Duplicate Publishing)**: 두 개 이상의 노드가 동일한 프레임 관계(`odom -> base_footprint`)를 중복 퍼블리시하면 타임스탬프가 교대로 점프하며 좌표가 비틀리지만, 시스템은 두 퍼블리셔 모두 정상으로 처리합니다.
- **좀비 프로세스 잔재**: 이전 세션의 브리지 프로세스가 완전히 종료되지 않고 감춰진 채 남아 `/clock`을 중복 퍼블리시하면 TF 버퍼가 불연속적으로 파손됩니다.

### 진단 원칙: 조용한 실패 현상을 규명하는 3대 검증 명령어

```bash
ros2 topic info /map -v                  # 1. QoS 호환성 검증 (TRANSIENT_LOCAL vs VOLATILE)
ros2 topic info /clock | grep Publisher # 2. Publisher count 단일성 확인 (반드시 1이어야 함)
ros2 run tf2_ros tf2_echo map odom       # 3. TF 타임스탬프의 불연속 점프 및 미래/과거 역전 여부 점검
```

> **정적 오류 대응 원칙**: 에러 로그가 비어있다고 해서 정상 작동을 의미하지 않습니다. 데이터 스트림 유실 시 가장 먼저 **QoS 프로필**, **Publisher 개수**, **타임스탬프 연속성**을 검증하십시오.

## 3. 상류 응답의 '성공' 판정에 숨겨진 타협을 경계하십시오

Nav2 Action Server가 반환값으로 `SUCCEEDED`를 전달했습니다.

```python
result = send_nav_goal(goal) # SUCCEEDED 성공 반환
# 하지만 로봇은 목표 지점에 미달한 전방 제자리에 멈춰 서 있음 (연속 가짜 성공 발생)
```

### 메커니즘 분석
항법 스택은 현실 물리적 제약을 고려하여 허용 오차 마진(`tolerance`)을 바탕으로 수행 여부를 판단합니다. 지정된 목표 좌표가 장애물 팽창 영역(Costmap Inflation Zone) 내에 위치할 경우, 전역 플래너는 접근 가능한 가장 인접한 타깃 좌표로 목표를 조정(Snap)합니다. **만약 조정된 인접 좌표가 로봇의 현재 위치와 동일하다면, 제어기는 물리적 이동을 수행하지 않은 채 즉시 성공으로 처리하여 판정을 반환합니다.**

> **성공 판정 해석 원칙**: 허용 오차를 내포한 시스템에서 반환되는 "성공"은 *요청한 오리지널 타깃*의 이행이 아닌, *시스템이 타협한 인접 타깃*의 완료일 수 있습니다.

### 원칙: 상류 시스템의 성공 판정을 기하학적 기준으로 직접 재검증하십시오

```python
result = send_nav_goal(goal)
if result == SUCCEEDED:
    # 로봇의 현재 위치 참값과 오리지널 목표 좌표 간 기하학적 거리를 직접 산출
    dist = get_distance(robot_pose, goal_pose)
    if dist > tolerance: # 타협된 가짜 성공(Pseudo-success) 감지 및 후속 처리
        handle_failure(goal)
```

### ⚠️ 함정: 실패 원인의 도메인을 구별하지 않은 일괄 차단 리스트 처리의 위험성

성공 응답뿐만 아니라 실패 처리 역시 정밀하게 분리해야 합니다. **반환된 실패 응답 코드는 "목표 지점 자체가 불가능한가"와 "현재 일시적 상태 문제인가"를 구분해 주지 않습니다.**

```python
if result == ABORTED:
    blacklist.add(goal)  # 선점(Preemption)까지 실패로 집계할 경우 정상 도달 지점이 영구 차단됨
```

- **선점 (Preemption)**: 신규 목표 전송으로 인해 진행 중이던 기존 목표가 취소되며 실패 응답이 반환됩니다. **이는 시스템 오류가 아니라 정상적인 미션 교체 동작입니다.**
- **서버 초기화 미완료**: 노드가 준비 단계에 있어 일시적으로 거절된 것일 뿐, 목표 좌표의 유효성과는 무관합니다.
- **통신 인터럽트**: 네트워크 트래픽 문제로 타임아웃이 발생한 경우입니다.

전자는 **영구 차단 리스트 등록** 대상이며, 후자는 **재시도(Retry)** 대상입니다. 이 둘을 구별하지 않고 일괄 처리하면 **시스템 스스로 도달 가능한 정상 영역들을 불가능한 구역으로 잘못 분류하여 자기 선택지를 축소시키는 심각한 오류**에 빠지게 됩니다.

> **실패 분류 원칙**: 실패 판정 시 **재시도 가능한 일시적 오작동**과 **영구히 기각할 유효성 오류**를 명확히 분리하십시오. 아울러 주행 이행 여부는 단순 이동 거리가 아닌 **목표 좌표까지 남아있는 남은 거리의 잔여 감소량**으로 계측해야 합니다. 복구 동작(Recovery behavior)이 포함된 스택에서 단순 이동량으로 진행을 판단하면 제자리 제자리 회전 및 왕복 이동을 정상 주행으로 잘못 인지하게 됩니다.

## 4. 파라미터 튜닝만으로는 극복할 수 없는 알고리즘의 구조적 한계

전역 경로가 장애물 벽면에 지나치게 밀착되어 생성됩니다. 경로를 이격시키기 위해 코스트맵 팽창 파라미터를 대폭 수정해 봅니다.

```yaml
# 팽창 관련 파라미터 범위를 극단적으로 조정해도 생성 경로에 변화가 없음
cost_scaling_factor: <극단적 하향> / <극단적 상향>
```

### 메커니즘 분석
**모든 알고리즘 라이브러리는 특정한 설계적 전제와 상수를 기반으로 동작합니다.**
NavFn 전역 플래너의 경우, 코스트 변환 계수가 컴파일 시점 상수로 고정되어 있어 런타임 설정 파일(YAML)로는 벽면 이격 거리를 조절할 제어 파라미터(Knob) 자체가 존재하지 않았습니다.

### 원칙: 파라미터 조정에 반응하지 않는다면 즉시 내부 소스코드를 분석하십시오

```cpp
// NavFn 소스코드 점검: 코스트 변환 계수가 상수로 하드코딩되어 있음을 확인
// 목적 함수를 런타임에 유연하게 제어 가능한 SmacPlanner2D 알고리즘으로 전환하여 벽면 밀착 문제 완벽 해결
```

> **튜닝 제1원칙**: 파라미터 범위를 크게 조율했음에도 출력 변화가 관측되지 않는다면, 즉시 파라미터 조 조정을 중단하고 해당 모듈의 소스코드를 열어 구조적 상수를 확인하십시오.

## 5. 센서는 물리적 관측 한계 내의 사실만을 전달합니다

2D 라이다 스캔 데이터가 정밀하게 발행되고 선반 기둥들이 점유 격자에 뚜렷하게 관측됩니다. 그러나 Nav2는 선반 상판 아래 빈 공간으로 경로를 생성하고, 로봇은 상판 구조물에 충돌합니다.

```
 [선반 상판 구조물] ──► 2D 라이다 스캔 평면보다 높게 위치하여 관측 불가능
     |          |
 =====|==========|===== ──► 2D 라이다 360° 스캔 평면
     |          |       ──► 기둥 4개만 점으로 관측되며, 기둥 사이 영역은 "자유 공간(Free Space)"으로 전송됨
```

### 메커니즘 분석
2D 라이다는 정해진 단일 물리 스캔 평면 외부의 입체 공간을 관측하지 못합니다. 센서는 **"자신이 관측할 수 없는 영역"을 관측 불가능으로 남겨두는 대신 "비어있는 자유 공간"이라는 적극적인 관측 데이터로 변환하여 전달**하므로 코스트맵이 해당 셀을 장애물이 없는 공간으로 지워버립니다.

### 원칙: 센서의 관측 메커니즘과 화각 특성에 적합한 소거 알고리즘을 배치하십시오

- **2D 라이다 (360° 전방위 넓은 화각)**: 광선 추적(Ray Clearing) 방식 적용 ── 로봇의 주행 궤적을 지나며 동일 평면을 반복 관측하므로 광선 궤적으로 기존 잔여 장애물을 제거
- **3D 뎁스 카메라 (전방 좁은 화각)**: 복셀 시간 감쇠(Voxel Decay) 방식 적용 ── 로봇 회전 시 동일 구역을 연속 관측할 수 없으므로 일정 시간이 경과하면 관측 데이터를 시간 감쇠로 소거

> **센서 활용 수칙**: 카탈로그 스펙보다 **해당 센서가 물리적으로 관측할 수 없는 사각지대가 어디이며 이를 어떻게 가공하여 보고하는지**를 우선적으로 정의하십시오.

## 6. 복합 알고리즘의 실질적 핵심 입력 계통을 파악하십시오

뎁스 카메라가 전방 벽면과의 거리를 밀리미터 단위의 오차로 정밀하게 퍼블리시하고 있습니다. 그러나 로봇이 이동하더라도 위치 추정이 갱신되지 않고 지도 포즈 그래프가 파손됩니다.

```
[무늬가 없는 단색 벽면] ──► 뎁스 거리 측정은 완벽히 작동함
                        ──► 그러나 RGB 영상 내 Visual Feature Point(특징점) 수율 0개 달성
                        ──► Visual Odometry 추적 파이프라인 완전 정지
```

### 메커니즘 분석
"RGB-D Odometry"라는 명칭으로 인해 뎁스 센서가 파이프라인의 핵심인 것처럼 오해하기 쉽지만, 실제 내부 처리 시퀀스는 다음과 같습니다:

1. **RGB 칼라 이미지에서 2D 특징점을 추출한다** (핵심 파이프라인)
2. 프레임 간 동일 특징점을 추적하여 2D Correspondence(대응)를 형성한다
3. 뎁스 데이터를 참조하여 추출된 특징점들에 3D 공간 좌표를 매핑한다
4. 두 3D 점군 간의 변환 행렬(Transformation Matrix)을 산출하여 로봇 변위를 계산한다

**뎁스 데이터의 역할은 3단계(3D 좌표 부여)에 국한됩니다.** 실제 로봇의 6자유도 변위를 계산하는 주체는 RGB 특징점이며, 뎁스는 3차원 스케일을 복원하는 보조 입력입니다. 무늬가 없는 평염한 벽면에서는 1단계(특징점 추출)에서 이미 실패하므로, 뎁스 데이터가 아무리 정밀하더라도 알고리즘 파이프라인 전체가 정지합니다.

> **입력 계통 분석 원칙**: 명칭에서 주역으로 느껴지는 입력 데이터가 실제 파이프라인의 핵심 의존성이 아닐 수 있습니다. 카탈로그 명세를 맹신하기보다 **"어떤 센서 입력 스트림이 유실될 때 파이프라인 전체가 마비되는가"**를 파악하십시오.

---

### ⚠️ 함정 1: 특징점 유실보다 잘못 매칭된 '오류 특징점'이 시스템에 더 치명적입니다

특징점 수율을 높이기 위해 벽면에 텍스처 패턴을 배치할 때, **동일한 패턴을 여러 장소에 반복 재사용해서는 안 됩니다.**

```
[A구역 벽면: 무늬 패턴 #5] ... [B구역 벽면: 무늬 패턴 #5] ──► 서로 다른 위치를 동일 장소로 오인
                                                         ──► 잘못된 Loop Closure 발생 ➔ Pose Graph 전체 붕괴
```

이를 인지 알고리즘 분야에서 **인지적 모호성(Perceptual Aliasing)**이라고 부릅니다. 루프 클로저는 "현재 관측 뷰와 가장 유사한 과거 뷰"를 맵 DB에서 검색하는 알고리즘이므로, 서로 다른 장소가 시각적으로 유사할 경우 **동일 장소로 오인하여 잘못된 제약 조건(Wrong Constraint)을 삽입**하고 이로 인해 전체 지도를 심각하게 비틀어 놓습니다.

**특징점 수율 부족은 위치 추정을 정지시킬 뿐이지만, 잘못 매칭된 특징점은 시스템이 정상으로 착각한 채 잘못된 좌표를 계속 산출하도록 만듭니다.** 후자가 시스템 전체의 붕괴를 초과하므로 훨씬 위험합니다.

> **완화 원칙**: Visual 특징점으로 Loop Closure 후보를 검색한 후, **기하학적 구조 데이터(LiDAR Scan Matching 등)를 통한 Cross-validation(교차 검증)**을 필수로 거치도록 설정하십시오. 시각 데이터와 기하 데이터는 상호 독립적인 실패 모드를 가지므로, 둘을 겹쳐 검증하면 오인식으로 인한 그래프 파손을 완벽히 방지할 수 있습니다.

---

### ⚠️ 함정 2: 스트림 해상도를 낮추었을 때 위치 추정 정밀도가 대폭 향상되었습니다

고해상도/고주기로 센서 프레임을 설정하면 정밀도가 올라갈 것으로 예상하지만, 제자리 피봇 회전 시 위치 추정 오차가 오히려 급증하는 현상이 발생합니다.

```
[RGB 프레임 t]  +  [Depth 프레임 t+Δ] ──► 회전 중 프레임 간 타임스탬프 불일치 발생
                                      ──► RGB 특징점에 엉뚱한 Depth 거리 값이 바인딩됨
```

RGB-D 파이프라인은 **동일 타임스탬프의 RGB 영상과 Depth 영상이 물리적으로 완전히 같은 시점의 장면을 관측했다는 전제**를 기반으로 작동합니다. 그러나 이미지 렌더링이나 버퍼 전송 오버헤드로 인해 타임스탬프 비동기화가 발생하면, 수 밀리초의 오차만으로도 회전 동작 시 특징점에 완전히 엉뚱한 깊이 정보가 바인딩됩니다. 회전 주행 시 시야각이 급격히 변하므로 오차가 극대화됩니다.

스트림 해상도를 다운스케일링하여 두 이미지 스트림이 타임스탬프 수준에서 완전히 동기화되도록 수정하자 위치 추정 오차가 획기적으로 감소하였습니다. **해상도 저하로 유실된 특징점 수율보다, 정확한 타임스탬프 동기화로 얻은 기하학적 정밀도 이점이 훨씬 컸기 때문입니다.**

> **센서 융합 원칙**: **다중 센서 파이프라인에서는 센서 단품의 해상도보다 센서 간 타임스탬프 시간 동기화(Temporal Alignment)가 최우선입니다.** 잘못 정렬된 고품질 데이터 두 개는, 완벽히 정렬된 저품질 데이터 두 개보다 치명적인 오차를 야기합니다.

## 7. 제어 정밀도는 정적 측정이 아닌 동적 실행 파이프라인에서 손실됩니다

로봇이 정지한 상태에서 비전 마커 포즈 추정 정밀도는 밀리미터 단위로 매우 우수합니다. 그러나 해당 추정 포즈를 바탕으로 Nav2 순정 연속 곡선 제어 접근(`opennav_docking`)을 수행하면 최종 접안 시 세로 오차가 크게 발생합니다.

```
[정지 상태 비전 측정 (고정밀)] ──► [연속 곡선 제어 주행 중 미세 제어 오차 누적] ──► [최종 접안 (큰 오차 발생)]
```

### 메커니즘 분석
정지 상태에서의 센서 측정 정밀도와 동적 주행 중인 제어기 이행 정밀도는 별개의 영역입니다. 연속 곡선 궤적 주행 시 휠 슬립과 모터 응답 지연으로 인해 제어 오차가 연속적으로 누적됩니다. **아무리 정밀한 초기 관측값이 있더라도, 주행 과정에서 누적되는 제어 오차를 상쇄할 보정 메커니즘이 없다면 정밀한 접안이 불가능합니다.**

### 원칙: 제어 파이프라인을 정지-측정-보정 단계별(Staging) 프로세스로 분리하십시오

```
[정지 및 전방 마커 측정] ──► [중간 회전점 이동 & 제자리 피봇 정렬] ──► [재정지 및 최종 포즈 보정] ──► [직진 후진 접안]
```

- 주행 궤적을 단계별로 끊어 정지 상태에서의 정밀한 비전 측정값을 최종 접안 자세로 그대로 복원
- 도킹 세로 오차를 밀리미터(mm) 단위로 대폭 정밀화 성공

## 8. 여유 마진은 물리적 규격과 위치 추정 오차가 공유하는 한정된 자원 예산입니다

로봇의 물리적 섀시 폭에 비해 좁은 통로의 공간 여유가 충분한 것으로 판단됩니다. 그러나 통로 진입 직후 로봇이 벽면에 접촉하며 오도메트리 좌표계가 붕괴합니다.

```
 [통로 벽면] |
            |← 공간 여유 →|  [실제 로봇 물리 위치]
            |              └──── SLAM 위치 추정 오차 (공간 여유 초과) ────┘  [로봇이 인지하는 위치]
            |
            * 로봇은 자신이 통로 중앙에 있다고 인지하지만 실제 하드웨어는 벽면을 긁고 있음
```

### 메커니즘 분석
로봇은 스스로 통로 중앙을 정상 주행하고 있다고 추정하지만, **SLAM 알고리즘의 위치 추정 오차(Localization Error)**가 통로 측면의 물리적 공간 마진보다 크면, 추정상 정상 주행 상태이더라도 실제 하드웨어 섀시는 벽면에 접촉하게 됩니다.

> **오차 예산 원칙**: **[위치 추정 오차] + [제어 진동 오차] + [물리적 공간 마진] = 단 하나의 한정된 자원 예산**

---

### ⚠️ 위험: 단순 접촉 오작동이 전체 맵 데이터 파손으로 전파됩니다

하드웨어가 벽면을 긁는 것으로 상황이 끝나지 않으며, 아래와 같은 연쇄 붕괴가 발생합니다:

```
벽면 접촉 ──► 휠 슬립 발생 ──► 휠 오도메트리 데이터 붕괴 ──► 어긋난 포즈로 센서 관측 데이터 생성
         ──► Pose Graph에 잘못된 Constraint 삽입 ──► SLAM 지도 전체 구조 파손
```

RTAB-Map과 같이 **전역 포즈 그래프 최적화(Global Graph Optimization)**를 수행하는 시스템에서는 단 한 번의 잘못된 제약 조건이 **멀리 떨어진 원격 구역의 지도 구조까지 통째로 비틀어 놓습니다.** 즉, "특정 구간에서의 미세한 주행 헤맴"이 "전체 맵 데이터 폐기"라는 치명적 결과로 전파됩니다.

> **시스템 평가 원칙**: **단순 미션 완주율과 같은 단일 지표로 자율주행 스택을 평가하지 마십시오.** 미션 목표 지점에는 도달했으나 내부 지도 데이터와 포즈 그래프가 완전히 파손된 정황을 놓치게 됩니다.

---

### 원칙: 단순 '진입 가능 규격'이 아닌 '제자리 회차 가능 규격'을 최소 통로 기준으로 설정하십시오

- 차동 구동 로봇의 제자리 회전 시 최소 요구 폭: **√2 × 로봇 섀시 폭**
- 안전 마진 기준을 회차 가능 폭으로 상향 조정
- 좁은 통로에서의 교착 및 오도메트리 붕괴 현상 완벽 방지

**진입 가능 조건과 이탈 가능 조건은 엄연히 다르며, 일반적으로 이탈 조건이 훨씬 혹독합니다.** 진입 규격만을 검증하면 로봇은 스스로 탈출할 수 없는 협소 구역으로 진입하여 정체됩니다.

## 9. 시뮬레이터는 답안지가 아닌 가설 검증용 가상 실험실입니다

가상 시뮬레이션 환경에서 CPU 사용량을 측정한 결과 특정 노드가 컴퓨팅 자원을 과도하게 소모하는 것으로 관측되었습니다. 이 수치를 바탕으로 실물 로봇 배포 자원 예산을 수립하면 심각한 과대평가가 발생합니다.

```
Gazebo /clock (1000 Hz 퍼블리시) ──► rclpy Python 시계 콜백 1000회 연속 호출 ──► CPU 점유율 급증 (실기에는 /clock 토픽 부하가 없음)
```

### 메커니즘 분석
시뮬레이터 자체가 생성하는 부가적인 환경 트래픽(`/clock` 1000Hz 등)이 측정 대상 프로세스의 부하와 뒤섞입니다. 가상 환경의 절대적인 측정치를 그대로 적용하면 측정 대상 노드가 아닌 **시뮬레이션 측정 환경 자체의 오버헤드**를 측정하게 됩니다.

### 원칙: 절대 수치가 아닌 '동일 환경 내 상대적 A/B 벤치마킹' 결과만을 추출하십시오

| 시뮬레이터에서 유효하게 검증 가능한 항목 | 실물 하드웨어 환경에서 재측정해야 할 항목 |
|---|---|
| 상태 머신 FSM 및 로직 상태 전이의 타당성 | 프로세스 자원 사용량의 절대 수치 (CPU / RAM RSS) |
| 알고리즘 A와 B 간의 상대적 성능 비교 | 실제 광학 센서의 노이즈 패턴 및 사각지대 |
| 노드 간 통신 인터럽트 및 정지 현상 유무 | 타이어 마찰력, 휠 슬립 및 정밀 도킹 물리 오차 |

## 10. 문제의 원인은 직관적 추측이 아닌 계측 데이터로 입증해야 합니다

로봇이 협소 구역에서 주행을 중단할 때 수많은 가설(CPU 자원 부족, Real-Time Factor 하강, 팽창 코스트 과다 등)을 세우고 실험을 반복합니다. 며칠 동안 가설에 따라 파라미터를 수정하지만 문제는 전혀 해결되지 않습니다.

### 메커니즘 분석
**진짜 원인은 초기 추측 가설 목록에 존재하지 않았습니다.** 막연한 직관에 의존하여 가설을 하나씩 검증하는 방식은 막대한 시간만을 소모시킵니다.

### 원칙 1: 직관적 추측을 멈추고 '시간과 컴퓨팅 자원이 어디에서 소모되었는가'를 정량 프로파일링하십시오

```python
# 원인별 소모 시간 배분 프로파일링(Profiling) 스크립트 실행
# 특정 서브시스템의 속도 출력 정체 시간이 길다는 것을 정량적으로 관측 ➔ 해당 모듈 내부 소스코드 수정을 통해 즉시 해결
```

> **프로파일링 원칙**: 막연한 가설 추론에 의존하지 말고 소모 시간과 컴퓨팅 자원의 정량적 프로파일링 배분표를 작성하십시오. 프로파일링 데이터는 올바른 가설을 도출해 주지만, 가설 추론만으로는 정량적 배분 현황을 파악할 수 없습니다.

---

### 원칙 2: 텍스트 로그에 의존하지 말고 관측 산출물을 시각화 프레임으로 출력하여 비교하십시오

로보틱스의 중간 산출물은 대부분 **원래 공간적 형태를 지닌 데이터**입니다 ── 지도, 코스트맵, 궤적 경로, 마커 검출 포즈, 3D 점군 데이터. 그러나 이를 단 한 줄의 텍스트 로그로 압축해 버리면 연속적인 데이터의 미세한 파손 현상을 전혀 발견할 수 없습니다.

```
[텍스트 로그만 관측할 때]   "탐사 노드가 이미 방문한 구역을 지속적으로 재방문함" ──► 원인 추적 불가능
[시각화 이미지 프레임 추출] 지도가 생성되다가 특정 프레임에서 '축소 파손되는' 현상 발견 ──► RTAB-Map 파라미터 원인 즉시 특정
```

> **시각화 원칙**: RViz2 및 이미지 렌더링 도구를 적극 활용하여 중간 산출물을 공간 이미지로 시각화하십시오. 텍스트 로그로는 수주간 파악하기 힘들었던 오류가 visual 프레임 비교를 통해 단번에 규명되는 경우가 많습니다.

---

### 원칙 3: 한 번에 단 하나의 변수만 변경하고, 기각된 가설을 반드시 기록하십시오

두 개 이상의 파라미터를 동시에 수정하면 순효과(Net Effect)만 관측됩니다. 성능이 향상되었더라도 부작용을 일으키는 나쁜 파라미터 변경까지 함께 안고 가게 됩니다.

아울러 현상은 개발자의 직관과 반대로 나타나는 경우가 많습니다. "검출 주기를 더 높이면 응답성이 좋아지겠지"라는 추측으로 주기를 극단적으로 늘렸으나, 이전 제어 명령이 수렴하기 전에 다음 명령이 개입하여 시스템 진동이 발생하는 식입니다. **따라서 반드시 계측해야 합니다.**

> **가설 기록 원칙**: 검증을 통해 기각된 가설과 실패 원인을 반드시 문서화하여 기록하십시오. 기각 기록이 없으면 추후 동일한 무의미한 테스트를 반복하게 됩니다. 기각된 가설 목록은 성공한 기록만큼이나 소중한 기술 자산입니다.

## 11. 초심자를 위한 권장 개발 순서 및 디버깅 가이드

### CLI 디버깅 진단 루틴 (ROS 2 핵심 디버깅 스크립트)

```bash
ros2 topic info <토픽명> -v       # QoS 호환성 프로필 검증 (조용한 실패 발생 원인 1순위)
ros2 topic info /clock          # Publisher count 단일성 검증 (반드시 1이어야 함)
ros2 run tf2_ros tf2_echo A B    # 좌표계 프레임 A-B 간 트랜스폼 정밀 조회
ros2 lifecycle get <노드명>      # Lifecycle 노드의 런타임 상태가 active인지 검증
```

---

### 권장 학습 및 구축 순서

1. **TF2 프레임 체계의 완벽한 이해**: 초보자가 겪는 문제의 상당 부분은 TF 프레임 붕괴에서 비롯됩니다. 표준 좌표계 규약(`map -> odom -> base_footprint -> sensors`)을 대충 넘기지 마십시오. 여기서 확실히 투자한 하루가 추후 수주일의 시간을 절약해 줍니다.
2. **통신 메커니즘 3종 및 QoS 프로필**: Topic, Service, Action의 쓰임새 차이와 QoS 호환성이 데이터 스트림에 미치는 영향력을 철저히 파악하십시오.
3. **Launch 파이프라인 및 Parameter 관리 아키텍처**: 시스템 규모가 확장될 때 가장 먼저 무너지는 영역입니다.
4. **대형 메인 스택 모듈 적용**: Nav2, RTAB-Map VSLAM 등 대규모 프레임워크로 확장하십시오.

## 마치며

ROS 2 자율주행 스택 개발 과정에서 가장 자주 마주치는 순간은 **로그는 비어있는데 로봇이 움직이지 않는 상황**입니다.

이 순간은 실패의 순간이 아니라, **"어떤 데이터를 계측하여 현상의 물리적 원인을 명확히 밝혀낼 것인가"**라는 엔지니어링 질문으로 전환되며 개발자로서 가장 크게 성장하는 지점입니다.

로봇은 가상이 아닌 실제 물리 세계에서 작동하기에 언제나 무수한 변수에 노출되어 있습니다. 단순한 미션 성공/실패라는 일시적 결과에 일희일비하기보다, **문제를 정밀하게 정의하고 데이터에 기반하여 원인을 명쾌하게 도출해 내는 분석 과정 자체**를 즐기시기를 응원합니다.
