# 성능 측정 도구

파라미터를 변경할 때 성능 변화가 '유의미한 차이인지' 판단하기 위한 도구 모음입니다.
모두 단독 실행 가능한 스크립트로 작성되어 별도의 빌드 과정이 필요 없습니다.

```bash
source /opt/ros/jazzy/setup.bash && source ~/ros2_ws/install/setup.bash
export ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST
python3 tools/<도구>.py
```

대부분의 도구는 전체 시스템 스택이 실행 중이어야 합니다 (`ros2 launch orinbot_navigation navigation.launch.py`).

| 도구 | 측정 대상 | 필요 환경 |
|---|---|---|
| `measure_load.py <라벨>` | 노드별 CPU/메모리 사용량 (고정 시나리오: c070 통로 왕복) | 전체 스택 |
| `map_quality.py <라벨>` | SLAM 위치 추정 오차 및 지도 흔들림 (c070+c090 왕복) | 전체 스택 |
| `corridor_test.py [폭...]` | 통로 폭별 직진 통과 가능 여부 및 소요 시간 | 전체 스택 |
| `turnaround_test.py [폭...]` | 통로 내 제자리 회전 가능 여부 (편심 스윕 테스트) | **시뮬레이터 전용** |
| `slam_accuracy.py` | 지정 동작 수행 후 SLAM 추정 위치 vs Gazebo 실제 위치 비교 | 전체 스택 |
| `stream_rates.py [초]` | 카메라 스트림별 실제 발행 주기 및 타임스탬프 동기화 상태 | 시뮬레이터 전용 |
| `jump_check.py [초]` | TF 발행자 중복 여부 및 map->odom / odom->base 좌표 점프 감지 | 전체 스택 |
| `render_map.py` | `/map` 토픽 데이터를 PNG 이미지로 저장하고 프론티어 표시 | 전체 스택 |
| `verify_frontier.py` | 현재 지도 상태에서 탐사 목표 후보 지점 추출 검증 | 전체 스택 |
| `dock_calib.py` | 도크 인식 정확도 + `external_detection_rotation_*` 산출 | 시뮬레이터 + 검출기 |
| `dock_range.py` | 마커 검출 거리·편차·무검출 구간 (거리 스윕) | **시뮬레이터 전용** |
| `dock_test.py [횟수]` | 반복 도킹 성공률과 실제 정렬 오차 | 전체 스택 |
| `corridor_plan.py` | 통로 폭별로 **전역 경로가 나오는지** | Nav2 활성 |
| `stall_attribution.py` | 로봇이 **한 구역을 못 벗어난 시간**을 원인별로 배분 | 전체 스택 |
| `path_stability.py` | 전역 경로 방향 변화량 vs 각속도 명령 부호 반전 빈도 | Nav2 활성 |
| `wrongway.py` | 경로가 요구하는 방향과 **반대로 도는 순간**을 기록 | Nav2 활성 |

> `corridor_plan.py` 는 주행 시험이 아니라 **경로 계획만** 확인합니다 (`ComputePathToPose` 직접 호출). 전역 코스트맵 형상(`footprint` / `robot_radius`), 벽 두께, `Grid/CellSize` 를 건드렸다면 이 도구로 다시 확인하세요 — 격자 이산화 때문에 통과 여부가 셀 단위로 끊깁니다.

> 아래 세 도구는 **"멈춰서 오래 생각하는" 증상을 원인별로 가르기 위한 것**입니다. 그 증상에는 서로 다른 원인이 섞여 있고 고치는 곳이 각각 다릅니다 — 목표가 없어서(탐사 노드) / 경로가 없어서(플래너) / 컨트롤러가 0 을 내서(MPPI) / 복구 중이라서(BT) / 명령은 나가는데 안 움직여서(끼임·twist_mux). `stall_attribution.py` 로 먼저 배분한 뒤, 컨트롤러 쪽이면 `path_stability.py`(경로가 뒤집히는가 vs MPPI 가 진동하는가)와 `wrongway.py` 로 좁힙니다.

## 필독 — 측정 결과가 왜곡되는 여섯 가지 주의사항

**1. `ps` 명령의 `%CPU` 수치를 사용하지 마세요.**
`ps`가 제공하는 수치는 프로세스 생성 시점부터의 평균값이므로 시나리오 수행 구간의 실제 부하가 낮게 희석됩니다. `measure_load.py`는 `/proc/<pid>/stat`의 utime+stime 차분 데이터를 활용하여 순간 사용률을 정밀하게 측정합니다.

**2. 동일한 세션에서 파라미터를 변경해가며 측정할 때 `rtabmap` 항목은 신뢰할 수 없습니다.**
시간이 지남에 따라 지도가 계속 누적 확장되므로 자원 사용량이 자동으로 증가합니다 (단일 세션 내에서 25% → 38% → 54%p 증가 관측). RTAB-Map 관련 비교 실험 시에는 **매 측정마다 전체 스택을 새로 기동해야 합니다.**

**3. 통과 가능 기준 이하(0.70 m 미만)의 통로를 테스트 시나리오에 포함하지 마세요.**
로봇이 갇히거나 끼여 복구 동작에 소비되는 시간이 샘플 데이터에 섞이면 "파라미터 변경 효과"와 "해당 회차의 끼임 정도"를 구분할 수 없게 됩니다. 이 때문에 측정 시나리오를 기존 c060에서 c070 통로로 변경했습니다.

**4. 로봇을 통로 내부로 직접 순간이동(Teleport)시키면 안 됩니다** (`turnaround_test.py`).
Gazebo는 정적 물체와의 초기 충돌 관통 현상을 물리적으로 밀어내지 않으므로, 벽에 80 mm 묻힌 상태 그대로 회전을 시도하게 됩니다. 반드시 통로 외부에서 직접 주행시켜 진입하도록 구성해야 합니다.

**5. 측정 스크립트를 두 개 동시에 돌리지 마세요.**
둘 다 로봇에 목표를 보내면서 서로를 밀어내(preemption) 결과가 전부 쓰레기가 됩니다. 실제로 `dock_test.py` 두 개가 겹쳐 돌면서 로봇이 도크에서 154 mm 벗어난 자리로 끌려갔습니다. 이전 측정이 끝났는지 반드시 확인한 뒤 다음을 시작하세요.

**6. 순간이동 후 대기할 때는 `sleep` 이 아니라 spin 해야 합니다.**
`rclpy` 구독 큐(깊이 10)에 이전 위치에서 찍힌 메시지가 쌓였다가 다음 수집 때 배달됩니다. 그러면 마커가 화각 밖으로 나간 자리에서도 "검출됨"으로 나오고 값은 이전 위치의 것이라, 검출 한계 거리를 실제보다 가깝게 잘못 재게 됩니다. `dock_range.py` 초기 측정에서 0.36 m 행이 0.42 m 행과 소수점 4자리까지 같게 나왔던 것이 이 현상입니다.

## 현재 성능 기준선 (2026-08-02)

> **아래 수치는 전역 플래너가 `NavFn` 이던 시절에 잰 것입니다.** 2026-08-03 에 `SmacPlanner2D` 로 바꾸고 MPPI 문턱값을 내렸으므로, 주행 시간·CPU 계열 항목은 다시 재야 합니다. 도킹과 도크 인식 수치는 플래너와 무관하므로 그대로 유효합니다.

**개발 PC 기준** — 파라미터 간 상대 비교용입니다.

| 항목 | 측정값 |
|---|---|
| CPU / 메모리 사용량 | 1.16 코어 / 1.38 GB |
| SLAM 위치 추정 오차 | 중앙값 0.027 m, 90 퍼센타일값 0.043 m |
| map→odom 최대 보정량 | 0.111 m |
| 도킹 성공률 | 3/3, 재시도 0회 (단계 분리, 중앙값 25.6초) |

| 도킹 정렬 오차 (곡선 접근) | 세로 20.3 / 22.7 mm, 가로 0.8 / 2.4 mm, 각도 0.4 / 1.8도 (중앙값 8.6초) |
