# Orin Nano 자원 예산 (실측 기반)

CLAUDE.md에서 분리된 참조 문서입니다. 자원 조율 시에만 필요한 상세 자료이므로 매 세션 상주시키지 않으며, 기타 실측 기록은 CLAUDE.md를 참고하세요.

타깃 보드 사양: 6코어 Cortex-A78AE 1.7GHz + 8GB **통합** 메모리 (CPU/GPU 공유).
코어당 연산 성능이 개발 PC(i7-14700K)의 1/4~1/5 수준이므로 리소스 여유가 적습니다.

측정 도구: `tools/measure_load.py` — 고정 시나리오를 수행하며 노드별 CPU/RSS 사용량을 주기적으로 샘플링합니다. 파라미터를 변경할 때마다 해당 도구로 "유의미한 성능 차이"인지 판단하세요. 지도 품질 평가 도구는 `tools/map_quality.py`입니다.

**평가 시나리오는 최소 통과 기준 이상의 통로만 경유합니다 (2026-08-02 변경 사항).**
`measure_load.py`는 c070(0.70 m), `map_quality.py`는 c070 + c090(0.90 m) 통로를 사용합니다.
과거에는 두 도구 모두 c060(0.60 m) 통로를 경유했으나, 최소 통과 가능 폭 기준을 0.70 m로 정한 이후로는 이 시나리오가 기준을 벗어나게 되었습니다. 해당 폭에서는 로봇이 자주 갇혀 복구에 긴 시간을 소모하고, 벽면에 긁히며 회전하다가 오도메트리까지 손상되므로, 측정 수치가 "파라미터의 효과"가 아닌 "해당 회차의 끼임 정도"를 반영하게 됩니다.
**따라서 이 기준 변경 전후의 수치 절대값은 서로 직접 비교해서는 안 됩니다.**

**측정 방식 관련 주의사항 (2026-08-02 수정)**

- 과거에는 `ps -eo pcpu` 수치를 사용했으나, 이 값은 **프로세스 기동 후 현재까지의 누적 평균값**입니다. 테스트 대상 노드들은 시나리오 시작 수 분 전에 미리 실행되어 대부분 대기 상태였으므로 주행 구간의 실제 부하가 낮게 희석되는 문제가 있었습니다. 현재는 `/proc/<pid>/stat`의 utime+stime 차분 수치를 활용합니다. **본 문서 표의 과거 측정 결과와 신규 측정 결과의 절대값을 직접 비교하지 마세요.**
- **동일한 세션에서 파라미터를 변경하며 비교할 경우 `rtabmap` 수치는 신뢰할 수 없습니다.**
  시간이 지남에 따라 지도가 지속적으로 확장되므로 자원 사용량이 저절로 증가합니다 (단일 세션 내 25% → 38% → 54%p 증가 관측). 파라미터 변경의 영향을 받는 노드만 선별하여 비교하거나, RTAB-Map 관련 측정 시 매번 스택 전체를 새로 기동해야 합니다.

**현재 기준선의 지도 품질 평가** (`map_quality.py`, c070+c090 통로 경유):
위치 자세 오차 중앙값 0.027 m / 90 퍼센타일값 0.043 m / 최대 0.061 m,
map->odom 최대 보정량 0.111 m, 5 cm 초과 보정 4회 / 101회 샘플.
향후 파라미터 변경 시 **위 측정 수치와 비교 검증**을 수행하세요.

- **`use_vslam:=false` 설정이 유일하게 유의미한 리소스 절감 효과를 제공합니다** (CPU -24%p, 메모리 -221MB).
  다만 이에 따른 반대 급부로 위치 추정 정확도가 하락합니다. 3m 왕복 주행 후의 오차:
  시각 오도메트리 적용 시 **0.072 m** / EKF 단독 적용 시 **0.209 m**.
  반면 헤딩 각도 오차는 자이로 성능 덕분에 EKF 단독 방식이 오히려 우수합니다 (0.44도 → 0.03도).
  단, 본 위치 오차는 Gazebo 휠 오도메트리 기준이므로 실제 기기 환경보다 비관적으로 평가된 수치입니다.
- **Nav2 파라미터 축소 시도는 실질적 리소스 절감 효과가 없었습니다.**
  MPPI 샘플 수 2000 → 1000, 룩어헤드 스텝 56 → 40, 로컬 코스트맵 해상도 0.02 → 0.04, BT 틱 주기를 100 → 33Hz로 모두 축소하여 적용했으나, `controller_server` CPU가 14.0% → 13.3%, `planner_server`가 11.4% → 11.7%로 유의미한 차이가 없었습니다. **따라서 모두 원상 복구하고 고품질 설정을 유지합니다.**
- **2026-08-02 추가 검증 시도 4건 — 채택 1건, 기각 3건:**
  - `controller_frequency` 20 → 10 Hz 하향: **기각.** MPPI 제어기에서 "제어 주기가 `model_dt`보다 길다"는 오류와 함께 configure 단계에서 실패하므로 `model_dt` 역시 0.05 → 0.1로 동시 변경해야 합니다. 이는 예측 지평이 2.8초 → 5.6초로 변경되는 **MPPI 제어 모델 자체의 변경**에 해당합니다. 얻은 이점은 `controller_server` CPU 17.5% → 13.5%p (단일 코어의 4%p 절감)에 불과한 반면 시나리오 주행 시간은 42초 → 46초로 늘어났습니다.
  - 전역 코스트맵 `raytrace_max_range` 12 → 5 m 축소: **기각.** `planner_server` CPU 사용량이 9.9% → 11.0%p로 오히려 미세하게 증가했습니다 (노이즈 수준).
  - **Nav2 컴포지션(Composition) 적용: 기각 (구조적 불가).** `nav2.launch.py` 내의 `use_composition:=true` 주석을 참고하세요. 컴포넌트 로딩 방식은 YAML 설정을 개별 파라미터로 분해하여 대상 노드에 전달하므로, 서버 내부에서 동적으로 생성되는 `local_costmap`/`global_costmap` 노드가 파라미터를 전달받지 못합니다. 실측 결과 기본 `static_layer`가 로드되면서 컨테이너 프로세스가 SIGSEGV 오류로 중단되었습니다.
  - `Rtabmap/DetectionRate` 2.0 → 1.0 Hz 하향: **절감 효과는 크나 기본값은 2.0 Hz를 유지합니다.** 아래 "RTAB-Map 메모리 관리" 절을 참고하세요.
- **`localization:=true` 설정은 자원 절감 옵션이 아닙니다.** 오히려 `rtabmap` CPU가 25.1% → **33.9%p**, 메모리가 552MB → **604MB**로 증가했습니다. `Mem/InitWMWithAllNodes: true` 설정에 의해 전체 지도 DB(당시 125MB)를 작업 메모리에 상주시키기 때문입니다. 이는 지도를 고정하기 위한 **동작 모드 선택**일 뿐 성능 최적화 옵션이 아닙니다. 자원 사용량은 DB 크기에 비례하여 증가합니다.
- **RTAB-Map 메모리는 용량 상한을 설정해야 합니다.** 제한을 두지 않으면 지속적으로 메모리가 증가합니다 (단일 세션에서 834MB → 1491MB, 장시간 기동 시 5GB 초과 관측). 이를 위해 `Rtabmap/MemoryThr` 기본값을 300으로 설정했습니다 (`memory_thr` 런치 인자).
- RViz 를 어디서 띄울지는 아래 "실기 배포 구성" 절을 참고하세요. 원격(개발 PC)으로 볼 때는 **양쪽 모두** `ROS_AUTOMATIC_DISCOVERY_RANGE=SUBNET` 이어야 합니다 (기본값 `LOCALHOST` 면 서로 안 보입니다). 다만 이 방식은 네트워크가 멀티캐스트를 통과시켜야 성립합니다 — 일부 공유기는 IGMP 스누핑으로 버립니다.

# 실기 실측 (2026-08-02) — 위의 "Orin 환산" 열을 대체합니다

**여기까지의 표는 전부 개발 PC 측정치를 4.5배 곱한 추정입니다. 실기가 준비되어 직접 쟀고, 결과는 추정치의 약 1/1.8 이었습니다.** 환산치(주행 5.6/6 코어)는 과대평가였습니다. 원인은 개발 PC 측정치 자체에 `/clock` 세금이 섞여 있었고 그 오염분까지 4.5배로 곱했기 때문입니다.

**앞으로 실기 예산 판단은 이 절의 수치를 쓰세요. 위 표는 "개발 PC 파라미터 간 상대 비교"용으로만 유효합니다.**

## 실기 환경

Jetson Orin Nano Super Developer Kit, L4T R39.2.0 (JetPack 7), Ubuntu 24.04.4, ROS 2 Jazzy(apt), NVMe 227 GB, 전력 모드 `MAXN_SUPER`, 유휴 51도.
`rtabmap` / `nav2` / `spatio_temporal_voxel_layer` / `robot_localization` / `depth_image_proc` / `opennav_docking` / `image_proc` 는 apt 로 이미 설치돼 있고 `cv2` 도 개발 PC 와 같은 4.6.0 입니다(ArUco 구 API 를 쓰므로 중요). 워크스페이스 빌드는 25초.
**스왑을 16 GB 추가했습니다** (`/swapfile`, `vm.swappiness=10`, fstab 등록). 기본 이미지에는 스왑도 zram 도 없어서 rtabmap 이 튀면 곧바로 OOM 입니다. swappiness 를 낮게 두는 이유는 스왑을 상시 계층으로 쓰면 주행 중 페이지 폴트가 제어 주기를 흔들기 때문입니다 — 목적은 안전망입니다.

## 측정 방법

개발 PC 시뮬에서 센서 토픽만 5분 bag 으로 뜨고(`ros2 bag record --use-sim-time`), Orin 에서 재생하며 **Gazebo 없이** 실제 인지·항법 스택을 돌렸습니다. 도구는 `tools/` 가 아니라 측정 전용 스크립트 3종입니다(`run_load.sh`, `proc_sampler.py`, `clock_tax.sh` — 세션 산출물이며 저장소에는 두지 않았습니다).
CPU 단위는 **코어 1개 = 100%** (6코어이므로 상한 600%). 3회 반복해 합계 330~335% 로 재현됨을 확인했습니다.

- **주행이 시작되면 +32 %p** 늘어납니다. 거의 전부 `controller_server`(+18.8)와 `bt_navigator`(+8.9)입니다.

- **`rgbd_odometry` + `rtabmap` 만으로 1.07 코어** 입니다. 절감을 논한다면 여기가 먼저입니다.
- **도킹 노드 2개가 아무 일도 안 하면서 0.62 코어** 를 씁니다. `dock_marker_board` 는 도크 근처가 아니어도 15 Hz 로 ArUco 검출을 계속 돌립니다. `~/pause` 서비스가 이미 있으므로 배선만 하면 회수됩니다.

## `/clock` 세금을 실기에서 직접 쟀습니다

아무 일도 안 하는 rclpy 노드 두 개를 같은 조건에서 비교:

| | CPU |
|---|---|
| `use_sim_time: true` (`/clock` 100 Hz 구독) | 11.5% |
| `use_sim_time: false` | 0.2% |
| **차이 = rclpy 노드 1개당 세금** | **11.3 %p** |

실기에는 `/clock` 자체가 없으므로 통째로 사라집니다. **다만 C++ 노드의 `/clock` 비용은 못 쟀습니다** — 그쪽도 0은 아니므로 위 합계는 그만큼 보수적인(높게 잡힌) 값입니다.

## 이 측정에서 두 번 무효 판정이 났습니다 (둘 다 "로그는 멀쩡한데 안 되는" 부류)

- **bag 녹화에 `--use-sim-time` 을 안 주면 측정이 통째로 무효가 됩니다.** 메시지 헤더는 시뮬 시각인데 bag 에 저장되는 수신 시각은 벽시계가 되어, `--clock` 재생이 어긋난 시계를 내보냅니다. 29초 뒤 VO 가 멈추고 rtabmap 이 "Did not receive data" 로 도는데 **노드는 전부 살아 있어서 CPU 표만 보면 정상으로 보입니다.** 확인법: `ros2 bag info` 의 Start 가 1970년대 작은 수치여야 합니다.
- **`use_sim:=false` 로 스택을 띄우면 카메라 포인트클라우드 컨테이너가 같이 빠집니다.** `sim.launch.py` 안에 정의돼 있기 때문인데, `/camera/depth/points` 는 STVL 3D 복셀 레이어의 **유일한** 관측원이고 정합 뎁스는 rtabmap 의 입력입니다. 실기에도 반드시 필요한 부하이므로 측정에서 빠지면 안 됩니다. 게다가 프로세스 이름이 `component_container` 라 노드 이름으로 집계하면 표에서도 사라집니다.

## 실기 배포 구성의 예산 — **추정입니다 (측정 아님)**

위 실측은 Gazebo 없이 bag 을 재생한 것이라 **실물 드라이버가 빠져 있고 RViz 도 없습니다.** 실배포 구성으로 옮길 때의 증감을 정리하면:

| 항목 | 증감 | 성격 |

| 실측 주행 스택 | 309% | **측정** |

### RViz 를 60~100% 로 잡은 근거

Orin 단독 실행 때 잰 **30.2% 는 RTF 0.2 에서 나온 값**입니다. 센서가 1/5 속도로 들어오고 있었고, RViz 비용은 대부분 메시지 구동이라 실속도에서는 그만큼 올라갑니다. 그리고 `navigation.rviz` 는 비싼 표시가 전부 켜져 있습니다:

- `PointCloud2 / StvlVoxels` — **가장 비쌈.** 복셀 0.05 m 격자를 갱신마다 GPU 로 업로드
- `Image / ColorImage` — 15 Hz 디코드
- `Map` 3개(map + 전역/로컬 코스트맵) — 갱신마다 전체 텍스처 업로드
- `PointCloud2 / Map3D` — `map_3d:=false` 가 기본이라 빈 토픽, 비용 0

**로봇에 모니터를 달아 실기에서 띄운다면 `navigation.rviz` 를 그대로 쓰지 마세요.** 위 셋을 빼고 `Map` + `LocalCostmap` + `RobotModel` + `Scan` + `Path` 만 남긴 2D 뷰를 별도 설정으로 만드세요 (20~30% 예상). 3D 진단이 필요하면 그때 개발 PC 에서 전체 구성을 원격으로 띄우면 됩니다. 그리고 RViz 는 상시 실행하지 마세요 — 로봇의 모니터는 사람이 옆에 있을 때만 봅니다. 별도 프로세스라 껐다 켜도 주행에 영향이 없습니다.

곁들여 `publish_voxel_map: false` (`nav2_params.yaml`) 로 두세요. **보는 쪽뿐 아니라 발행하는 쪽 부하도 같이 줄어듭니다** — STVL 레이어는 주행 중 34.7% 인 `controller_server` 안에 있습니다.

**아직 숫자로 못 잡은 위험 두 가지:**
- **통합 메모리 대역폭은 CPU% 에 안 잡힙니다.** RViz 가 GPU 로 데이터를 올리는 동안 rtabmap 이 같은 대역폭을 씁니다.
- **발열.** RViz 없이 60.1도였습니다. 디스플레이 출력 + GPU 렌더가 얹혔을 때 `MAXN_SUPER` 유지가 되는지 확인이 필요합니다.

## 아직 못 밝힌 것

**부하 중에는 `ros2 topic hz` 를 믿을 수 없습니다.** 같은 측정에서 입력 뎁스 9.5 Hz, 출력 정합 뎁스 13.6 Hz 가 나왔습니다 — 출력이 입력보다 클 수 없으므로 측정 도구 자체가 메시지를 놓치고 있습니다. 따라서 `/camera/depth/points` 가 낮게(2~6 Hz) 읽힌 것이 실제 프레임 드롭인지 판정하지 못했습니다. 노드 내부 카운터로 다시 재야 합니다.
