# Orin Nano 자원 예산 (실측 기반)

CLAUDE.md에서 분리된 참조 문서입니다. 자원 조율 시에만 필요한 상세 자료이므로 매 세션 상주시키지 않으며, 기타 실측 기록은 CLAUDE.md를 참고하세요.

타깃 보드 사양: 6코어 Cortex-A78AE 1.7GHz + 8GB **통합** 메모리 (CPU/GPU 공유).
코어당 연산 성능이 개발 PC(i7-14700K)의 1/4~1/5 수준이므로 리소스 여유가 적습니다.

측정 도구: `tools/measure_load.py` — 고정 시나리오를 수행하며 노드별 CPU/RSS 사용량을 주기적으로 샘플링합니다. 파라미터를 변경할 때마다 해당 도구로 "유의미한 성능 차이"인지 판단하세요. 지도 품질 평가 도구는 `tools/map_quality.py`입니다.

**평가 시나리오는 최소 통과 기준 이상의 통로만 경유합니다 (2026-08-02 변경 사항).**
`measure_load.py`는 c070(0.70 m), `map_quality.py`는 c070 + c090(0.90 m) 통로를 사용합니다.
과거에는 두 도구 모두 c060(0.60 m) 통로를 경유했으나, 최소 통과 가능 폭 기준을 0.70 m로 정한 이후로는 이 시나리오가 기준을 벗어나게 되었습니다. 해당 폭에서는 로봇이 자주 갇혀 복구에 긴 시간을 소모하고, 벽면에 긁히며 회전하다가 오도메트리까지 손상되므로, 측정 수치가 "파라미터의 효과"가 아닌 "해당 회차의 끼임 정도"를 반영하게 됩니다.
**따라서 이 기준 변경 전후의 수치 절대값은 서로 직접 비교해서는 안 됩니다.**

**측정 방식 관련 주의사항 (2026-08-02 수정)**

- 과거에는 `ps -eo pcpu` 수치를 사용했으나, 이 값은 **프로세스 기동 후 현재까지의 누적 평균값**입니다. 테스트 대상 노드들은 시나리오 시작 수 분 전에 미리 실행되어 대부분 대기 상태였으므로 주행 구간의 실제 부하가 낮게 희석되는 문제가 있었습니다. 현재는 `/proc/<pid>/stat`의 utime+stime 차분 수치를 활용합니다. **본 문서 표의 과거 측정 결과와 신규 측정 결과의 절대값을 직접 비교하지 마세요.**
- **동일한 세션에서 파라미터를 변경하며 비교할 경우 `rtabmap` 수치는 신뢰할 수 없습니다.**
  시간이 지남에 따라 지도가 지속적으로 확장되므로 자원 사용량이 저절로 증가합니다 (단일 세션 내 25% → 38% → 54%p 증가 관측). 파라미터 변경의 영향을 받는 노드만 선별하여 비교하거나, RTAB-Map 관련 측정 시 매번 스택 전체를 새로 기동해야 합니다.

**실측 결과 (실물 기기에 기동되는 노드만 합산, RViz/Gazebo/브리지 제외):**

| 구성 조건 | CPU | 메모리 | Orin 환산 | 측정 방식 |
|---|---|---|---|---|
| 초기 기준선 | 1.09 코어 | 1.93 GB | 4.9 / 6 | 과거 `ps` 방식 |
| EKF 추가 (시각 오도메트리 유지) | 1.15 코어 | 1.85 GB | 5.2 / 6 | 과거 `ps` 방식 |
| **EKF만 사용 (`use_vslam:=false`)** | **0.90 코어** | **1.63 GB** | **4.0 / 6** | 과거 `ps` 방식 |
| 기준선 (선반 추가 후, c060 경유) | 1.16 코어 | 1.37 GB | 5.2 / 6 | 신규 `/proc` 방식 |
| `detection_rate:=1.0` (c060 경유) | 1.05 코어 | 1.26 GB | 4.7 / 6 | 신규 `/proc` 방식 |
| `localization:=true` (c060 경유) | 1.21 코어 | 1.42 GB | 5.5 / 6 | 신규 `/proc` 방식 |
| **현재 기준선 (c070 경유)** | **1.24 코어** | **1.42 GB** | **5.6 / 6** | 신규 `/proc` 방식 |

**현재 기준선의 지도 품질 평가** (`map_quality.py`, c070+c090 통로 경유):
위치 자세 오차 중앙값 0.027 m / 90 퍼센타일값 0.043 m / 최대 0.061 m,
map->odom 최대 보정량 0.111 m, 5 cm 초과 보정 4회 / 101회 샘플.
향후 파라미터 변경 시 **위 측정 수치와 비교 검증**을 수행하세요.

- **`use_vslam:=false` 설정이 유일하게 유의미한 리소스 절감 효과를 제공합니다** (CPU -24%p, 메모리 -221MB).
  다만 이에 따른 반대 급부로 위치 추정 정확도가 하락합니다. 3m 왕복 주행 후의 오차:
  시각 오도메트리 적용 시 **0.072 m** / EKF 단독 적용 시 **0.209 m**.
  반면 헤딩 각도 오차는 자이로 성능 덕분에 EKF 단독 방식이 오히려 우수합니다 (0.44도 → 0.03도).
  단, 본 위치 오차는 Gazebo 휠 오도메트리 기준이므로 실제 기기 환경보다 비관적으로 평가된 수치입니다.
- **Nav2 파라미터 축소 시도는 실질적 리소스 절감 효과가 없었습니다.**
  MPPI 샘플 수 2000 → 1000, 룩어헤드 스텝 56 → 40, 로컬 코스트맵 해상도 0.02 → 0.04, BT 틱 주기를 100 → 33Hz로 모두 축소하여 적용했으나, `controller_server` CPU가 14.0% → 13.3%, `planner_server`가 11.4% → 11.7%로 유의미한 차이가 없었습니다. **따라서 모두 원상 복구하고 고품질 설정을 유지합니다.**
- **2026-08-02 추가 검증 시도 4건 — 채택 1건, 기각 3건:**
  - `controller_frequency` 20 → 10 Hz 하향: **기각.** MPPI 제어기에서 "제어 주기가 `model_dt`보다 길다"는 오류와 함께 configure 단계에서 실패하므로 `model_dt` 역시 0.05 → 0.1로 동시 변경해야 합니다. 이는 예측 지평이 2.8초 → 5.6초로 변경되는 **MPPI 제어 모델 자체의 변경**에 해당합니다. 얻은 이점은 `controller_server` CPU 17.5% → 13.5%p (단일 코어의 4%p 절감)에 불과한 반면 시나리오 주행 시간은 42초 → 46초로 늘어났습니다.
  - 전역 코스트맵 `raytrace_max_range` 12 → 5 m 축소: **기각.** `planner_server` CPU 사용량이 9.9% → 11.0%p로 오히려 미세하게 증가했습니다 (노이즈 수준).
  - **Nav2 컴포지션(Composition) 적용: 기각 (구조적 불가).** `nav2.launch.py` 내의 `use_composition:=true` 주석을 참고하세요. 컴포넌트 로딩 방식은 YAML 설정을 개별 파라미터로 분해하여 대상 노드에 전달하므로, 서버 내부에서 동적으로 생성되는 `local_costmap`/`global_costmap` 노드가 파라미터를 전달받지 못합니다. 실측 결과 기본 `static_layer`가 로드되면서 컨테이너 프로세스가 SIGSEGV 오류로 중단되었습니다.
  - `Rtabmap/DetectionRate` 2.0 → 1.0 Hz 하향: **절감 효과는 크나 기본값은 2.0 Hz를 유지합니다.** 아래 "RTAB-Map 메모리 관리" 절을 참고하세요.
- **`localization:=true` 설정은 자원 절감 옵션이 아닙니다.** 오히려 `rtabmap` CPU가 25.1% → **33.9%p**, 메모리가 552MB → **604MB**로 증가했습니다. `Mem/InitWMWithAllNodes: true` 설정에 의해 전체 지도 DB(당시 125MB)를 작업 메모리에 상주시키기 때문입니다. 이는 지도를 고정하기 위한 **동작 모드 선택**일 뿐 성능 최적화 옵션이 아닙니다. 자원 사용량은 DB 크기에 비례하여 증가합니다.
- **RTAB-Map 메모리는 용량 상한을 설정해야 합니다.** 제한을 두지 않으면 지속적으로 메모리가 증가합니다 (단일 세션에서 834MB → 1491MB, 장시간 기동 시 5GB 초과 관측). 이를 위해 `Rtabmap/MemoryThr` 기본값을 300으로 설정했습니다 (`memory_thr` 런치 인자).
- RViz는 실물 기기에서 실행하지 말고 개발 PC에서 원격 접속으로 확인하세요. 원격 접속 시에는 **양쪽 PC 모두** `ROS_AUTOMATIC_DISCOVERY_RANGE=SUBNET`으로 설정해야 합니다. (현재 기본값인 `LOCALHOST` 설정 시에는 타 PC에서 검색되지 않습니다.)
