# Orin Nano 자원 예산 (실측)

CLAUDE.md 에서 옮겨 왔습니다. 자원 조율을 할 때만 필요한 참조 자료라
매 세션 상주시키지 않습니다. 다른 실측 기록은 CLAUDE.md 에 있습니다.


목표 보드: 6코어 Cortex-A78AE 1.7GHz + 8GB **통합** 메모리(CPU/GPU 공유).
코어당 성능이 이 PC(i7-14700K)의 1/4~1/5 수준이라 여유가 없습니다.

측정 도구: `tools/measure_load.py` — 고정 시나리오를 돌리며 노드별
CPU/RSS 를 샘플링합니다. 파라미터를 바꿀 때마다 이걸로 "유의미한 차이"인지
판단할 것. 지도 품질은 `tools/map_quality.py`.

**시나리오는 기준 안쪽 통로만 지납니다 (2026-08-02 변경).**
`measure_load.py` 는 c070(0.70 m), `map_quality.py` 는 c070 + c090(0.90 m).
예전에는 둘 다 c060(0.60 m)을 지났는데, 최소 통과 가능 폭을 0.70 m 로
정한 뒤로는 기준 밖입니다. 거기서는 로봇이 자주 끼여 복구에 시간을 쓰고
벽에 갈리며 돌다 오도메트리까지 깨지므로, 재는 것이 "파라미터 효과"가
아니라 "그날 얼마나 끼였나"가 됩니다.
**이 변경 전후의 절대값은 비교하지 마세요.**

**측정 방법 주의 (2026-08-02 수정)**

- 예전에는 `ps -eo pcpu` 를 썼는데 이 값은 **프로세스가 뜬 뒤 지금까지의
  평균**입니다. 노드는 시나리오 시작 몇 분 전에 떠서 대부분 놀고 있었으므로
  주행 구간의 실제 부하가 희석돼 낮게 나왔습니다. 지금은
  `/proc/<pid>/stat` 의 utime+stime 차분을 씁니다. **이 표의 옛 행과 새 행은
  절대값을 섞어 비교하지 마세요.**
- **같은 세션에서 파라미터를 바꿔가며 비교할 때 `rtabmap` 항목은 못 믿습니다.**
  지도가 계속 자라기 때문에 시간이 갈수록 저절로 올라갑니다
  (한 세션 안에서 25 -> 38 -> 54 %p 로 관측). 바꾼 것이 영향을 주는 노드만
  비교하거나, RTAB-Map 이 관련되면 매번 전체를 새로 띄울 것.

**실측 결과 (실기에 남는 노드만 합산, RViz/Gazebo/브리지 제외):**

| 구성 | CPU | 메모리 | Orin 환산 | 측정법 |
|---|---|---|---|---|
| 기준선 | 1.09 코어 | 1.93 GB | 4.9 / 6 | 옛 `ps` |
| EKF 추가 (시각 오도메트리 유지) | 1.15 코어 | 1.85 GB | 5.2 / 6 | 옛 `ps` |
| **EKF 만 (`use_vslam:=false`)** | **0.90 코어** | **1.63 GB** | **4.0 / 6** | 옛 `ps` |
| 기준선 (선반 추가 후, c060 경유) | 1.16 코어 | 1.37 GB | 5.2 / 6 | 새 `/proc` |
| `detection_rate:=1.0` (c060 경유) | 1.05 코어 | 1.26 GB | 4.7 / 6 | 새 `/proc` |
| `localization:=true` (c060 경유) | 1.21 코어 | 1.42 GB | 5.5 / 6 | 새 `/proc` |
| **현재 기준선 (c070 경유)** | **1.24 코어** | **1.42 GB** | **5.6 / 6** | 새 `/proc` |

**현재 기준선의 지도 품질** (`map_quality.py`, c070+c090):
자세오차 중앙값 0.027 m / 90%값 0.043 m / 최대 0.061 m,
map->odom 최대 보정 0.111 m, 5cm 넘는 보정 4회/101.
앞으로 파라미터를 바꾸면 **이 두 줄과 비교**할 것.

- **`use_vslam:=false` 가 유일하게 큰 절감입니다** (CPU -24%p, 메모리 -221MB).
  대가는 위치 정확도입니다. 3m 왕복 후 오차:
  시각 오도메트리 **0.072 m** / EKF 만 **0.209 m**.
  각도는 오히려 EKF 가 낫습니다 (0.44도 -> 0.03도, 자이로가 좋아서).
  단 이 위치 오차는 Gazebo 휠 오도메트리 기준이라 실기보다 비관적입니다.
- **Nav2 파라미터 축소는 효과가 없었습니다.** MPPI 표본 2000->1000,
  스텝 56->40, 지역 코스트맵 0.02->0.04, BT 틱 100->33Hz 를 전부 적용했는데
  `controller_server` 가 14.0 -> 13.3%, `planner_server` 11.4 -> 11.7% 로
  차이가 없었습니다. **전부 원복하고 품질 좋은 값을 유지합니다.**
- **2026-08-02 추가 시도 4건 — 채택 1건, 기각 3건.**
  - `controller_frequency` 20 -> 10 Hz: **기각.** MPPI 가 "제어 주기가
    `model_dt` 보다 길다"며 configure 에서 죽으므로 `model_dt` 도 0.05 ->
    0.1 로 같이 올려야 합니다. 즉 예측 지평이 2.8초 -> 5.6초로 바뀌는
    **MPPI 모델 변경**입니다. 얻은 것은 `controller_server` 17.5 -> 13.5 %p
    (코어의 4%p) 뿐이고 시나리오 시간은 42 -> 46초로 늘었습니다.
  - 전역 코스트맵 `raytrace_max_range` 12 -> 5 m: **기각.**
    `planner_server` 9.9 -> 11.0 %p 로 오히려 늘었습니다(잡음 수준).
  - **Nav2 컴포지션: 기각 (구조적으로 안 됨).** `nav2.launch.py` 의
    `use_composition:=true` 주석 참고. 컴포넌트 로딩은 YAML 을 개별
    파라미터로 풀어 해당 노드에만 붙이므로, 서버 안에서 따로 만들어지는
    `local_costmap`/`global_costmap` 노드가 설정을 못 받습니다.
    실측: 기본 `static_layer` 가 로드되고 컨테이너가 SIGSEGV.
  - `Rtabmap/DetectionRate` 2.0 -> 1.0: **효과는 크지만 기본값은 2.0 유지.**
    아래 "RTAB-Map 메모리" 절 참고.
- **`localization:=true` 는 자원 절감이 아닙니다.** 오히려 `rtabmap` 이
  25.1 -> **33.9 %p**, 552 -> **604 MB** 로 늘었습니다.
  `Mem/InitWMWithAllNodes: true` 로 DB 전체(당시 125 MB)를 작업 메모리에
  올리기 때문입니다. 지도를 고정한다는 **동작 선택**이지 성능 선택이
  아닙니다. 값은 DB 크기에 비례해 커집니다.
- **RTAB-Map 메모리는 상한을 걸어야 합니다.** 무제한이면 계속 자랍니다
  (한 세션에 834MB -> 1491MB, 장시간 뒤 5GB). `Rtabmap/MemoryThr`
  기본값을 300 으로 두었습니다 (`memory_thr` 런치 인자).
- RViz 는 실기에서 띄우지 말고 개발 PC 에서 원격으로. 그때는 양쪽 모두
  `ROS_AUTOMATIC_DISCOVERY_RANGE=SUBNET` 으로 바꿔야 합니다
  (지금 값 `LOCALHOST` 로는 다른 PC 가 안 보입니다).
